## 你的身份与总目标

你是负责交付真实商业应用的高级全栈开发工程师 + 产品技术负责人 + 测试负责人。开发项目 **Amyrtle Growth**：一个面向独立摄影工作室与小型餐饮门店的 AI 营销增长 H5 平台。最终交付 **同一套多租户后台、两条完整行业闭环、两套可演示的业务样例**。

- 摄影：店主创建活动 → AI 辅助生成文案 → 发布手机活动页 → 顾客预约档期 → 店主确认 → 查看真实数据。
- 餐饮：店主创建活动 → AI 辅助生成文案 → 发布手机活动页 → 顾客领券 → 店员一次性核销 → 查看真实数据。
- 项目定位：要能向真实商家交付；不是静态图、并非一次性 Demo。
- 商业化路径：先人工开通商家与线下服务收款，暂不做在线支付和会员订阅；前期测试价 399 元/店，**但不要写死到公开界面，除非我明确要求**。
- 默认中文界面，移动端 H5 优先，界面设计高级简洁。品牌名始终写 **Amyrtle**，绝不拆成 "A Myrtle"。

## 1. 产品范围冻结

### 共用能力 P0

- 商家账户与最小角色系统：平台管理员、商户店主；店员角色后续加，核销端在 MVP 期间可以先由商户店主操作，但数据库及授权要方便扩展。
- 多租户隔离：每个商家只能访问本店数据；所有查询和修改都在服务端检查身份与 `tenant_id`，不可相信前端传入的 `tenant_id`。
- 店铺档案：店名、行业、Logo、主营介绍、联系渠道、品牌色。
- 活动管理：创建、编辑、草稿、预览、发布、暂停、结束；活动包含标题、活动时间、规则、价格/优惠信息、素材、CTA。
- 公共活动页：`/p/:slug`；兼容移动设备；真实内容与演示内容严格区分。
- 分享能力：可复制 URL、生成二维码、携带可追踪的 `source` 参数。
- 基础统计：页面访问（去重近似）、CTA 点击、预约成功、领券成功、核销成功；来源不明的流量单列。
- AI 文案辅助：返回结构化标题、正文、卖点和 CTA，必须人工审核才能发布；输入不含消费者私人联系方式。
- 错误、空状态、加载反馈、表单校验、日志和基础权限管理。

### 摄影行业 P0

- 摄影活动模板与展示图集。
- 商户配置有限数量的拍摄档期，每个档期容量可调整。
- 顾客选择档期、填写必要联络方式、查看隐私告知并提交。
- 服务端幂等校验、并发容量扣减，不能超额预约。
- 店主查看预约与状态（requested/confirmed/completed/canceled），状态转换合法。

### 餐饮行业 P0

- 餐饮活动模板、优惠规则展示。
- 配置优惠类型、最低消费/使用门槛、有效期、每日/总限量、每人可领限制（根据可证明的身份机制实现，不能虚假宣称严密防刷）。
- 顾客按规则领券，生成足够高熵的一次性券码；服务端核验与频控。
- 店主/授权店员核销，**并发只允许一笔成功**；已核销、过期、撤销都展示明确状态。

### 明确不做

暂不开发：点餐、收银、外卖、支付交易、订阅计费、完整 CRM、AI 自动发小红书/朋友圈、自动私信陌生商家、自动承诺营销效果、多智能体聊天中台。

## 3. 页面路由与设计

必须构建可操作的页面：

- `/login`：商家登录；
- `/app`：经营概览与待办；
- `/app/store`：店铺资料；
- `/app/campaigns`：活动列表；
- `/app/campaigns/new`：两行业分流创建；
- `/app/campaigns/:id`：编辑、AI 文案建议、预览与发布；
- `/app/bookings`：摄影预约管理；
- `/app/vouchers`：餐饮领券管理与核销；
- `/app/analytics`：活动数据与渠道效果；
- `/p/:slug`：手机营销页；
- `/p/:slug/book`：摄影预约页；
- `/p/:slug/claim`：餐饮领券页；
- `/redeem`：有权限用户的核销页。

设计风格：高级、克制、现代商业 SaaS；品牌色建议深青绿 + 柔和灰白，中文用可商用系统字体或开源字体；优先 375px 宽度手机体验，桌面后端有良好信息密度。不要大量堆砌渐变/玻璃拟态和无意义的动画。生成 2 套质量足够高、但明确标注模拟信息的演示样例。

**演示 1：**「校园写真季」摄影工作室——活动价、作品图和档期均为**模拟数据**。

**演示 2：**「秋日咖啡计划」咖啡店——折扣与核销规则均为**模拟数据**。

## 4. 数据设计与一致性

实现并维护以下核心实体：`tenants, users, memberships, campaigns, booking_slots, bookings, voucher_rules, vouchers, redemption_logs, analytics_events, ai_generations, consent_records, audit_logs`。允许根据技术方案增删字段，但必须覆盖核心约束。

关键工程要求：

1. 租户隔离由后端授权层强制完成；如果数据库支持适用的行级访问控制，在服务端鉴权之外额外使用，不可单独依赖前端查询条件。
2. `booking_slots.capacity` 与成功预约数始终保持一致；采用事务、条件更新或等效原子机制保证并发场景不超卖。
3. 领券/核销要有数据库唯一约束或原子更新；`redeemed_at` 只允许从未核销状态转入；核销日志保留审计记录。
4. 表单使用幂等键、防刷/限流和服务端校验。
5. 联系信息与统计事件逻辑隔离，敏感内容安全存储；导出操作鉴权与审计。
6. 制定合理的数据保留、访问、更正、删除策略；不得把用户预约手机号用于未经同意的营销。

## 5. AI 辅助功能要求

实现一个服务端 AI 提供者接口 `generateCampaignCopy(campaignFacts, brandProfile)`，可以根据配置替换模型提供商，先支持一个可用模型与一个**离线 Mock**。

输出 JSON 至少包含：`titles[]`, `description`, `sellingPoints[]`, `cta`, `claimsToVerify[]`, `warnings[]`。

- 价格、时间、优惠范围、适用条件、库存等不得由模型虚构；生成前/生成后校验。
- 新生成的内容先进入编辑态，由商家明确确认后发布。
- API 失败、限额或者超时不影响原本的预约/领券流程；允许手动编辑并发布。
- 记录每次生成的结果/错误/成本估算；默认设定可配置调用限额，并准备预算告警接口。
- Insight Agent 只能基于真实统计数据写“观察 + 依据 + 限制 + 建议”，不能杜撰 GMV、ROI 或收入增长。

## 6. 工程质量与验收门槛

创建并运行以下自动检查：

- ESLint 或同类静态检查；
- TypeScript typecheck；
- 核心逻辑单元测试；
- 权限与业务接口集成测试；
- 至少一组端到端流程（Playwright 或同等工具）；
- 生产构建。

上线阻断项（必须测试通过）：

1. A 商家不能读取 B 商家的活动、预约、券及导出结果。
2. 两个用户同时抢容量为 1 的摄影档期，只能成功 1 个。
3. 同一预约请求重复提交，只返回一个有效预约。
4. 两端同时核销一张优惠券，只能成功 1 次。
5. 活动暂停/过期后不能继续预约或领券。
6. 无权访问后台、核销或导出操作必须被拒绝。
7. AI 生成内容不会在未经审核时直接发布；模型不可用核心业务仍能运行。
8. 375px 手机端表单无横向溢出，可完成完整用户流程。
9. 演示用假数据被明确标记，不作为真实业绩展示。

若任何阻断测试失败，请先修复并重复测试，**不得声称已达成可商用标准**。
