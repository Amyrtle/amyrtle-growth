## 01  项目决策摘要

> **产品不卖“AI”，而卖“更快发布营销活动 + 更清晰地管理结果”。**

| 项目要素 | V1.0 决策 |
| --- | --- |
| 目标客户 | 桐乡及杭州周边独立摄影工作室、校园附近咖啡店/烘焙店等小型餐饮门店 |
| 场景边界 | 摄影：活动宣传 + 预约管理；餐饮：活动宣传 + 领券核销 |
| 产品形态 | 移动端优先的 H5 活动页 + 桌面/移动双端商家后台 |
| 销售方式 | 先试点部署服务，目标报价 399 元/店（测试价）；后续验证订阅 |
| 技术原则 | 一套多租户底座，两个垂直场景模板；AI 仅处理文案建议与基于事实的复盘 |
| 绝不首做 | 点餐收银、外卖、在线交易抽佣、复杂会员体系、全自动社媒发帖、万能 Agent |
| 商业验证 | 先访谈、再演示、再收取订单，防止无需求开发 |

### 成功标准：不是功能数量，而是商业闭环

1.  能在 10 分钟内创建并发布一项摄影或餐饮活动（测试目标）。

2.  摄影顾客完成预约，餐饮顾客领取并到店核销优惠券，数据可真实回溯。

3.  商家可以查看来源渠道和有效行动，不将访问量等同于营收。

4.  至少有 1 家真实商户愿意为明确交付物付费；不以测试/虚构数据代替成交。

### 明确的项目治理规则

- 商家活动公开发布、正式环境部署、外部收费、发送消息、购买云服务均需开发者审批。
- 每个版本形成 Git 提交、测试结果、可回滚部署；严格区分演示数据与真实数据。
- 试点只允许有限数量的商户手动开通，避免初期开放注册产生垃圾账户与滥用费用。
## 02  市场假设与用户画像

### 价值主张与关键待验证假设

| 假设 | 客户表达的真实问题 | 验证方式 / 判定 |
| --- | --- | --- |
| H1：摄影 | 微信私信、档期登记与活动宣传分散 | 访谈≥5家；至少2家确认痛点；演示后愿意进入具体报价 |
| H2：餐饮 | 活动券发放、人工核销与传播效果不透明 | 访谈≥5家；至少2家愿做短期活动试验 |
| H3：付费 | 商家愿为可运行的活动工具付费，而不只是看页面 | 至少1家同意明细报价并完成真实付款 |
| H4：留存 | 每月重复举办活动的商家可能愿意持续付费 | 试点结束追问是否续用；记录拒付原因 |

### 用户角色

- 平台拥有者（Platform Admin）：管理试点商户、访问平台级匿名化指标、处理支持工单。
- 店主（Merchant Owner）：维护店铺资料、创建活动、查看本店报名和核销数据。
- 店员（Staff，P1）：仅核销本店优惠券/管理本店预约，不得改套餐和导出全部线索。
- 消费者（Visitor）：无需注册即可访问活动页；仅在预约/领券时提交必要信息。
### 差异化定位

不替代美团/抖音、小程序点餐、传统收银系统。强调“活动营销微站 + 轻量闭环 + AI 运营建议”，尤其适合短期专题活动、联名活动、新品发布、校园主题活动。

建议优先选择「已有社媒账号、每月至少做一次活动、暂时没有统一报名系统」的商家。避免和没有活动营销需求的商户反复推销。

## 03  核心用户路径

### A｜摄影店：营销页—预约—复盘

1.  店主登录 → 创建“校园写真季”，填价格、时间、作品图、服务细则。

2.  AI 根据店主真实输入生成标题、卖点与传播文案；店主人工校对并确认。

3.  选择摄影模板 → 生成 /p/{slug} 公开活动页 → 获取二维码和来源追踪链接。

4.  消费者选择可用档期 → 填联系方式、确认隐私说明 → 提交预约。

5.  系统事务性锁定档期名额，生成预约编号；店主后台可标记确认/取消/已到店。

6.  后台展示访问、有效预约、预约来源和到店记录（需商家主动更新）。

### B｜餐饮店：促销页—领券—核销—复盘

1.  店主录入优惠活动、使用门槛、有效期、可用时段、每日或总名额。

2.  AI 生成活动文案 → 商家复核 → 发布移动端促销页面。

3.  顾客扫码查看活动，按规则领取一张可核验优惠券。

4.  顾客到店展示动态或一次性券码；店员在核销端验证并执行核销。

5.  系统以服务端原子操作确保“一券只核一次”，记录门店、时间、操作者。

6.  统计领券数、核销数及渠道来源；不得推断没有接入的支付成交额。

### C｜平台运营者：复制一个案例

创建商家账户 → 套用行业模板 → 协助录入素材 → 生成演示 → 商家确认 → 试运行 → 导出复盘 → 讨论下一次活动。尽量将部署操作固化成标准清单。

## 04  范围冻结与优先级

| 优先级 | 必须交付 | 延后交付 |
| --- | --- | --- |
| P0｜双行业可跑通 | 手动开通商户、登录、活动草稿/发布、双模板、AI文案、预约名额原子控制、领券一次性核销、基础埋点、隐私告知、核心权限与审计 | — |
| P1｜可向商家交付 | 来源二维码、受控数据导出、店员最小权限、删除申请处理、活动复制、商家操作手册和回滚演练 | — |
| P2｜验证后决定 | 完整订阅计费、在线支付、复杂 CRM、A/B测试、短信通知、朋友圈自动发布、点餐外卖/收银、模板商城 | 首次试点不做 |

### 统一交互原则

- 所有营销页以移动端 375px 设计为基准；后台支持桌面效率视图。
- 每个表单字段明确必填、错误提示、提交中状态、成功结果，避免多次点击重复提交。
- 活动页必须有商家名称、实际活动规则、有效期和联系渠道；演示页标注“演示用”。
- 默认模板可配置品牌色/图片/文字，不允许用户直接注入自定义脚本。
## 06  功能需求与可验收用户故事

| ID｜功能 | 用户故事 | 验收条件 |
| --- | --- | --- |
| F01 商户隔离 | 作为店主只看本店数据 | 所有读取/写入服务端检验 tenant_id；跨店访问返回403/404 |
| F02 创建活动 | 店主能在5分钟内填完活动资料 | 必填校验完整；草稿可保存与编辑 |
| F03 生成文案 | 店主点击生成更专业的活动文案 | 输出结构化内容；价格与日期只能来自真实输入；不自动发布 |
| F04 公开页面 | 店主分享活动链接 | 可预览、发布、暂停、到期自动不可领券/预约 |
| F05 摄影预约 | 顾客选档期并留下必要信息 | 确认页出现预约编号；容量冲突不超卖 |
| F06 预约状态 | 店主可确认/取消预约 | 状态流转合法且留下操作审计 |
| F07 餐饮优惠券 | 顾客可以领取合格优惠券 | 达到领取/库存上限时正确拒绝；同一身份与券种限制可配置 |
| F08 一次性核销 | 店员核销顾客优惠券 | 重复核销返回已核销；并发请求仅成功一次 |
| F09 渠道追踪 | 店主区分二维码渠道 | 同一活动不同渠道可分享；数据口径明确 |
| F10 概览数据 | 店主看活动漏斗 | 访问/预约/领券/核销均由真实事件计算 |
| F11 授权与删除 | 消费者了解数据用途并可申请删除 | 告知文本、用途与撤回渠道可用；相关数据按适用规则处理 |
| F12 导出审计 | 店主导出本店活动数据 | 有权限用户才能导出且审计记录可查 |

### 状态机定义

Campaign: draft → published → paused / ended；paused → published（仅活动未过期）；ended 不再接受新预约/领券。

Booking: requested → confirmed → completed / canceled；requested → canceled；禁止 canceled 直接变 completed。

Voucher: issued → redeemed / expired / revoked；核销为不可重复事务。若需纠错，必须管理员执行带日志的逆向补偿流程，不直接改旧日志。

## 07  数据库与多租户设计

推荐优先评估 CloudBase PostgreSQL。最终由 Codex 对照当前 CloudBase 能力确认认证、数据库部署、权限与迁移方案；若改用云开发文档数据库，必须明确替代的数据一致性实现。

| 表名 | 核心字段（示例） | 关键约束 |
| --- | --- | --- |
| tenants | id, name, industry, plan, status, created_at | 独立商家主键；不在客户端信任 tenant_id |
| users / memberships | user_id, tenant_id, role, status | 商户角色绑定；角色从服务端识别 |
| campaigns | id, tenant_id, type, slug, status, config_json, starts_at, ends_at | slug唯一；活动归属不可修改 |
| booking_slots | id, campaign_id, start_at, end_at, capacity, reserved_count | capacity ≥ reserved_count；事务/原子操作防超订 |
| bookings | id, tenant_id, campaign_id, slot_id, contact_encrypted, status | 请求幂等键；用户联系资料加密 |
| voucher_rules | id, tenant_id, campaign_id, quota, per_person_limit, terms | 发行容量与领券规则在服务端判定 |
| vouchers | id, tenant_id, rule_id, code_hash, status, issued_at, redeemed_at | 服务端唯一随机码；防遍历；单次核销 |
| redemption_logs | id, voucher_id, actor_id, redeemed_at, result | 核销与日志写入同一事务/可靠流程 |
| analytics_events | id, tenant_id, campaign_id, event_type, source, ts, anon_id | 不存不必要个人字段；去重口径 |
| ai_generations | id, tenant_id, campaign_id, input_snapshot, output, tokens, status | 商户可追溯审核；成本可统计 |
| consent_records | id, tenant_id, subject_ref, notice_version, time, purpose | 记录适用处理依据、告知与同意信息 |
| audit_logs | id, tenant_id, user_id, action, target_id, time | 仅允许受控访问、不能在普通后台删除 |

### 重要的数据完整性规则

- 每个商户业务表包含 tenant_id；查询条件、对象归属、后台角色三层校验。
- 预约名额扣减必须放在数据库事务或等价的原子检查中，处理同时提交。
- 优惠券码仅保存不可逆校验信息（如带密钥散列），公开链接使用高熵令牌，避免可枚举。
- 活动统计与客户手机号/邮箱分离；禁止将手机号码直接作为公开券码。
- 为 campaign_id, tenant_id, created_at 等高频条件建索引；迁移使用版本文件而非手工改表。
## 08  API 合约与接口安全

| 接口示例 | 方法 | 行为与校验 |
| --- | --- | --- |
| /api/auth/session | GET | 获取登录态与当前商户角色；无凭据401 |
| /api/campaigns | GET/POST | 获取本商户活动 / 创建草稿；服务端注入tenant_id |
| /api/campaigns/:id | PATCH | 更新本商户草稿；发布后关键条款变更需记录版本 |
| /api/campaigns/:id/publish | POST | 检查资料、规则、审核后发布 |
| /api/ai/copy | POST | 生成结构化AI建议；配额限制、内容审查 |
| /api/public/:slug | GET | 只返回公开可展示字段，不暴露后台配置 |
| /api/public/:slug/book | POST | 隐私告知、字段校验、幂等、档期原子扣减 |
| /api/public/:slug/claim | POST | 规则检查、反滥用、券码发放 |
| /api/vouchers/redeem | POST | 须店员认证；单次原子核销并记录审计 |
| /api/analytics/summary | GET | 角色与tenant授权；仅本店聚合数据 |
| /api/export/bookings | GET | 店主权限+审计；敏感导出有时限链接 |

### 统一响应约定

成功：{ ok: true, data, requestId }；失败：{ ok: false, error: { code, message }, requestId }。明确定义 400/401/403/404/409/429/500，避免在错误信息中暴露内部 SQL 或鉴权信息。

高风险接口：公开报名/领券加防刷、IP/会话限流、幂等键和验证码或等价挑战（按风险启用）；AI生成接口限制单店与全站日调用额度。

## 09  AI Agent / 模型工作流

> **Agent 在 V1 中是“副驾驶”，不是自主经营者。生成建议可自动化，公开发布与收费必须人审。**

| 能力 | 输入 | 输出 / 校验 |
| --- | --- | --- |
| Creative Agent | 行业、店铺定位、活动事实、商家上传素材 | 标题×3、正文×2、CTA、海报方向；不编造金额/时间/优惠 |
| Campaign Agent | 商家已确认的活动配置 | 模板参数、页面区块与预览配置；不能直接改数据库权限 |
| Insight Agent | 真实来源与汇总指标 | 7日简报：发现/证据/局限/下次可尝试的动作；不声称因果 |
| Internal QA Agent | 代码、PRD、测试清单 | 生成测试建议、审查差异；不能未经授权上线 |

### AI JSON 输出结构（建议）

{ "titles": ["..."], "subtitle": "...", "sellingPoints": ["..."], "cta": "...", "claimsToVerify": ["..."], "complianceWarnings": ["..."] }

### 内容安全与成本控制

- 价格、截止日、产品承诺、库存等事实字段由商家输入，模型只能重写表述；后端进行事实比对。
- 默认每商户每月设定 AI 额度（例如 30 次营销文案生成作为试点假设），触达后先提示，不自动超额付费。
- 保留人工编辑和模板回退；AI接口失败不会中断预约/领券的核心流程。
- 模型请求在服务端进行，记录消耗、失败率和响应时间；不得把消费者联系方式输入第三方模型作为默认分析素材。
## 10  数据埋点、指标与经营复盘

| 事件名 | 触发时机 | 业务用途 |
| --- | --- | --- |
| page_view | 公开活动页进入且通过基础过滤 | 曝光趋势，区分估算UV与PV |
| cta_click | 点击预约/领券按钮 | 衡量兴趣，不算有效线索 |
| booking_submit_success | 预约事务成功提交 | 摄影核心转化事件 |
| booking_confirmed | 商家确认预约 | 有效预约的次级质量指标 |
| voucher_claimed | 领券成功 | 餐饮漏斗中间层 |
| voucher_redeemed | 核销事务完成 | 餐饮核心转化事件 |
| campaign_published | 活动进入发布状态 | 商家侧产品使用指标 |

### 指标定义

摄影预约转化率 = 成功提交的有效预约数 / 活动页去重访问数（去重口径需展示）；餐饮核销率 = 已核销券数 / 实际发放券数。低样本量需提示波动，不直接得出“活动成功/失败”结论。

来源归因：使用 source/utm_campaign 参数与后台生成的分享链接。将“未知来源”独立保留，禁止把未追踪流量强行归因到某个平台。

展示“统计截止时间、分母定义、样本量”。除非有交易接口/商家核对成交数据，否则不展示 GMV、ROI、实际收入增长等数值。

## 11  非功能要求与上线安全底线

| 维度 | 验收目标（试点目标，不是外部保证） |
| --- | --- |
| 移动端 | 主流手机浏览器可用；375px宽不横向溢出；输入框不被键盘遮挡 |
| 性能 | 常规公开页缓存命中时目标LCP < 2.5s（良好网络）；需要实测并记录 |
| 稳定性 | AI 不可用时发布与预约仍可依靠手动文案继续进行 |
| 鉴权 | 未登录不可读取后台；跨商户API读写/导出100%拒绝 |
| 并发 | 同档期最多预约至容量上限；同优惠券不能被并发核销两次 |
| 审计 | 活动发布、修改优惠规则、导出线索、核销均留操作者与时间 |
| 备份 | 上线前确认云数据库备份与恢复能力，实际演练至少一次 |
| 可用性 | 所有关键动作包含状态提示和可恢复错误信息 |
| 无障碍 | 表单标签、键盘焦点、可读对比度、图片替代文本 |
| 成本 | 部署和外部API付费动作先询问开发者；配置预算告警 |

### 隐私与合规边界

- 消费者仅在预约/领券需要时提交最少必要信息；明确告知收集目的、接收方、保存期限和权利行使渠道。
- 营销消息订阅与完成预约所必需的信息处理分开，不预勾选营销同意，不默认批量发广告。
- 优惠券折扣条件、适用门店、最低消费、有效期必须如实表述。AI产出上线前人工核验。
- 中国大陆对外上线之前，依据实际业务模式、主体、服务器/域名等核查备案、许可、个人信息和税务要求；不要将“能部署”误认为“已具备商业经营资格”。
## 12  商业模式、报价与单位经济

### 首批试点服务（建议起售价 399 元/店）

| 包含内容 | 边界与交付说明 |
| --- | --- |
| 1个活动页 | 摄影或餐饮二选一；最多1次核心活动上线 |
| 基础配置 | 店铺资料、活动文案审核、手机适配与二维码 |
| 预约/核销 | 对应行业1套完整操作流程 + 后台培训 |
| 售后 | 建议7日试运行支持；明确响应方式和合理工作量 |
| 修改 | 建议2轮活动内容修改，不含临时扩增系统功能 |
| 不包含 | 广告投放费用、素材版权采购、短信费用、复杂定制、保底获客承诺 |

报价 399 元是试点假设，应依据真实开发工时、云/模型消耗、售后工作量与商家需求调整。建议签署简明服务确认单，写明交付清单、验收方式、退款/终止及数据处理责任。

### 可复用的利润核算公式

订单贡献毛利（未计本人时间） = 收入 − 云资源增量 − 模型调用 − 支付/平台费 − 直接素材成本。经营利润还须扣除本人沟通、部署、售后工时与其他管理费用。

示例情景（仅计算演示，不代表市场价格）：399 − 25（云资源） − 15（模型） − 9（其他直接成本）= 350元订单贡献毛利；如实际需要5小时服务，须把工时机会成本另行计入。

SaaS 订阅仅在试点验证重复举办活动和续用意愿后再推出；不要在功能不稳定时预售长期会员。

## 13  商户调研与成交 SOP

### 客户名单：先小规模、强针对性

首轮各选择5家商户做高质量访谈，之后扩大至20家。优先找已有活动营销需求且可以联系到店主的门店。公开地址/账号只用于合理调研，避免自动批量私信与采集私人手机号。

### 5个核心访谈问题

1.  你最近一次活动是怎么宣传的？谁来负责？花了多久？

2.  顾客预约/领券是通过什么方式记录的？发生过哪些遗漏或重复？

3.  活动结束后，你怎么判断活动有效？哪些数据最想知道？

4.  如果有一个工具能把这几步连起来，什么前提下你会愿意试用？

5.  如果我们帮你配置一次完整活动，你觉得合理收费是多少？为什么？

### 获客漏斗与回访

| 阶段 | 动作 | 衡量 |
| --- | --- | --- |
| 名单 | 整理10–20家与场景匹配的商家 | 是否明确活动需求 |
| 沟通 | 预约10分钟访谈，不硬推产品 | 访谈完成数 |
| 演示 | 用商家许可信息生成行业Demo | 愿意继续了解数 |
| 报价 | 给出399元试点交付明细 | 报价接受/拒绝理由 |
| 试点 | 明确起止、培训、售后与复盘 | 真实付费与再次使用意愿 |

> **成交过程中不承诺“必定新增客户”“保底增长XX%”，只承诺可验收的软件交付和约定服务。**

### 不通过即暂停的 Go / No-Go 闸门

- G1 需求闸门：访谈后仍无明确痛点，则不加功能，重新选择客户细分。
- G2 技术闸门：跨店隔离、核销防重、档期不超订任一失败，不对外提供真实服务。

- G4 扩张闸门：至少2个试点完整交付且售后负担可控，再评估会员订阅和新行业。
